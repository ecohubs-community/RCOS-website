## 1. Summary

1. **The content source moves from markdown to YAML.** Markdown becomes a generated output (for downloads), not something we edit. The site already generates YAML from the markdown (`scripts/build-standard-data.mjs` → `static/downloads/standard/rcos-core/0.1/*.yaml`), and RCOS-compass vendors exactly those files. We **flip the pipeline**: the YAML becomes the source, and markdown, docx, odt and the Compass data are built from it.
2. **One data model for every page about the standard**: chapters and clauses, glossary, templates (artifacts), guidance, stress tests and layers. Pages that are not about the standard (home, hubs, safeguards, reference implementations) become Svelte pages. Their copy lives in i18n files, not in markdown.
3. **Two layouts.** A *site* layout (header + footer, no sidebar) for everything, and a *standard* layout (left contents rail, right "on this page" rail, guide sheet) that is used only inside the standard itself.
4. **Strict styling rules.** Design tokens live in Tailwind `@theme`, and markup uses Tailwind classes only. Inline styles, `<style>` blocks and imperative DOM code are allowed only in a short list of exceptions, and lint rules enforce this.
5. **SEO and performance by default.** Every public page is prerendered, URLs are stable (redirects if any URL changes), JSON-LD is chosen per page type, fonts are self-hosted, icons are compiled at build time, and the video and podcast embeds use click-to-load facades.

### 2.4 Bugs in the design to fix while implementing
- **Mega menu behind the left sidebar.** The header is `sticky; z-index:40` and the mega panels are its children, so they cannot rise above its stacking context. The sidebar is `sticky; z-index:45`, so it covers the panels. Fix: use one z-index scale (§6.4) where the header sits above every in-page layer.
- **Guide sheet behind the header.** The sheet uses a hard-coded `top: 68px` (desktop) or `0` (compact), while the header is 68px **plus a 1px border**, and on compact screens it also has a sticky sub-bar at `top:68px`. Its z-index and offset come from separate hard-coded numbers, so they drift apart. Fix: the sheet becomes a real dialog layer from the scale and is positioned with a measured `--header-h` CSS variable, never a literal value.
- **Layout is computed in JavaScript** (`window.innerWidth` decides `isDesktop`, grid columns, sidebar position and so on). With SSR or prerendering this renders the desktop layout and then jumps. Everything becomes CSS breakpoints.
- **Accessibility gaps:**
  - Term triggers are `span role=button` with hover-only behaviour.
  - The guide is an `aside role=dialog` without focus management.
  - Small grey labels (`#9ca3af` on `#fbfbf9` at 11px) fail WCAG AA contrast.
  - Badges are 10.5px.
  - Copy icons are `#b8bdb0`.
- **Severity legend mixes two dimensions.** "High / Medium / Also involves L0" puts severity and relevance in one dot. Fix: the dot shows severity only, and the list is grouped into "Primarily tests this layer" and "Also touches this layer".
- **Every link in the design is an absolute `rcos.ecohubs.community/articles/...` URL**, and the GitHub link points at `ecohubs-community/RCOS-website` (the remote is `regenerative-community-blueprint`). All of these become generated, locale-aware routes.

## 4. Content architecture: YAML as the source

### 4.1 Why YAML is the right call (and what would be better)

Alternatives considered:

| Option | Verdict |
|---|---|
| Keep md as source, extract more | We already do this. Extracting by regex and position is fragile: translations are joined *by position*, guidance would need yet more `<details>` conventions, and stress-test data is split between frontmatter and prose. It gets worse with every feature. |
| A headless CMS / database | Loses git review, PR-based governance of the standard and offline builds. Overkill for one standard plus 22 templates. |
| JSON | Same model as YAML, but worse for long prose and comments. |
| **YAML source + schema + generators** | **Recommended.** Diffable, reviewable in PRs, comment-friendly for long prose, and already the format Compass consumes. A schema makes it safe. |

The one real improvement on "plain YAML" is to **pair it with a schema and a validator**, plus a small **reference syntax** for links (§4.5). Without both, YAML just moves the fragility somewhere else.

### 4.2 Authoring format and published format are different on purpose

- **Authoring format** (what we edit, in `content/`): English source files plus **per-locale sibling files** that contain only translated strings. Each entry carries a `sourceHash`. This keeps the existing translation workflow (`<base>.<lang>.*`, `sourceHash`, `translate.mjs`, `check-translations`), and lets us re-translate only the strings that changed.
- **Published format** (generated, in `static/downloads/standard/…`): the current Compass contract, i.e. one file per kind with inline `i18n: {en, de, …}`, plus the new kinds. Compass keeps working unchanged. A `schemaVersion` field and a published JSON Schema let Compass validate it.

> Why not inline `i18n` in the source too? Five languages inline make every file five times longer. Any EN edit then touches a file translators work in, and per-string drift detection needs extra bookkeeping. The build merges cheaply, so we author in the shape that is best for editing and publish in the shape that is best for consuming.

### 4.5 Links inside YAML: references, not URLs

Today, content links are hard-coded paths such as `/articles/rcos-core/v0-1/layer-0-identity-scope#21-purpose-definition`. That is how the broken home links happened. In YAML, prose uses **typed references** that the build resolves for each target (website per locale, absolute URL in downloads, plain text in Compass data):

| Syntax | Resolves to |
|---|---|
| `[[§2.3.4]]` / `[[§2.3]]` | Clause / section anchor in the right chapter |
| `[[layer:2]]` | Layer 2 chapter (label "Layer 2" / "Schicht 2" per locale) |
| `[[template:purpose-charter]]` / `[[template:purpose-charter#primary-purpose]]` | Template page / section |
| `[[test:founder-informal-veto]]` | Stress test |
| `[[term:invariant]]` | Explicit glossary popover (overrides auto-matching) |
| `[[Custom label\|§2.3]]` | Any of the above with a custom label |

Clause text is the exception: it stays plain natural language ("as defined in Layer 2"). Keywords, "Layer N" and glossary terms in it are detected automatically (§4.8), because clause wording is the standard and must not carry markup. The validator fails the build on any unresolved reference.

### 4.6 Guidance: what goes where (answers "can the guide live in the YAML?")

Yes. The guidance needs one rule so that the same text never lives in two places:

| Content | Lives on | Why |
|---|---|---|
| **In short** | spec **section** (`2.3`) | It summarises the rule, so it belongs to the rule. |
| **Common questions** (`q`, `a`, optional `ref`) | spec **section** | Questions are about the rules. `ref` enables "See §2.3.4" and the per-clause "?" button, which replaces the design's hard-coded `NOTES` map. |
| **Why it matters** | template **section** (`rationale`) | This is the existing rationale text, reused 1:1. |
| **How to fill it in** | template **section** (`instructions`) | Existing, reused 1:1. |
| **Examples, not recommendations** | template **section** (`examples`) | This is where a community writes its answer, which is the same place Compass shows them. |
| **What to cover** (prompts) | template **section** (`prompts`) | Moved upstream from Compass `annotations.yaml`. |
| **The question** (plain language) | template **section** (`question`) | Also moved upstream from Compass. The home page's "What RCOS is" cards use exactly this ("Why do we exist — in one sentence that's still true in ten years?"), and so can template pages and search. |
| **Put into practice** | *derived* | Template sections whose `clauses` fall in the spec section. No authoring needed. |
| **Tested by** | stress test `tests: [§…]` | Authored on the test, so one edit updates every page. It can be pre-filled from `preventsWith` → template → `clauses` and then reviewed by hand. |

The guide sheet for §2.3 is assembled at build time: section `inShort`, then the `rationale` and `examples` of the template sections that **own** §2.3's clauses (via `ownership.yaml`, so this matches Compass exactly), then section `questions`. The panel names its source ("From the Invariants Register template").

Every guidance field is marked **non-normative** in the schema and in the UI ("Guidance explains the rules. It never adds or changes them."). The validator enforces that guidance cannot contain RFC keywords in capitals, so it cannot look normative.

**Compass:** the published data gains `question`, `prompts` and `examples` on sections, and a new `specSections.yaml` (inShort, questions). Compass then drops those three fields from its own `annotations.yaml` and keeps only what is genuinely tool UX: `effort` and `dependsOn`. Compass's rule that "a question must cover what its section owns" moves into this repo's validator, together with the ownership checks.

### 4.7 Completing the examples (Q-14)

Sources, merged during migration (phase 2) and reviewed by hand:
1. **Compass `main` `annotations.yaml`**: `examples` and `prompts` for 92 and 94 sections. The gaps are concentrated in Layers 0–2. Imported verbatim and keyed by section key.
2. **Template placeholders.** 115 EN placeholders carry an inline example, e.g. `_<Asset 2, e.g. the community website and its domain.>_`. The migration splits each one into:
   - a neutral **placeholder** (`Asset 2`),
   - an **example** (`The community website and its domain.`), capitalised and with "e.g." removed.

   Duplicates of Compass examples are dropped. Translations are split the same way, and the counts are asserted per locale.
3. **Layer guides** (`rcos-layers/*`). They hold examples such as "Land cannot be sold.", which the design uses for §2.3. These are attached to the matching template section.
4. **Gaps.** Sections that are still without examples after 1–3 are listed by the validator as a *warning* (not an error) and are drafted in phase 4.

Rules for examples (validator plus review):
- They are written as one community's actual rule ("not recommendations").
- They contain no capitalised RFC keywords.
- They never cover what a sibling section owns.

### 4.8 Tooltips: data in YAML, behaviour in Svelte

- **Definitions** are content. They need translation, they appear in Appendix A, and Compass uses them. So they live in the glossary YAML, with per-locale `aliases`.
- **Matching** happens at build or prerender time, in a server-side tokenizer (not in the browser, and not by regex in a component). It turns each clause into typed parts: `text | keyword | layerRef | clauseRef | term`. Rules:
  - only the first occurrence of each term per section is marked (as in the design);
  - longest alias wins;
  - matching uses word boundaries and respects the locale;
  - `[[term:…]]` forces a match and `[[nolink:…]]` suppresses one.
- **Rendering** is a Svelte `Term` component built on an accessible popover primitive. It is a focusable `<button>`, works on hover *and* focus/tap, closes on Esc, and links to the glossary. The same tokenizer feeds keyword chips (`MUST`, `MAY`), whose tooltip text comes from `standard.yaml` → `keywords`, and Layer links, whose tooltip shows the layer name and question.

### 6.2 The "no inline styles, no plain JS" rule

**Default:** Tailwind classes in markup, and Svelte (runes, events, `bind:`, `{@attach}`) for behaviour.

**Allowed exceptions** (each must carry a comment that names the exception):
1. `style:--var={value}` for genuinely dynamic numbers, e.g. popover coordinates or a measured header height. A CSS custom property, never a full declaration.
2. SVG geometry attributes in the layer ring diagram (`cx`, `cy`, `r` are attributes, not styles).
3. The inline pre-paint script in `app.html` (theme, reading mode, collapsed rail), which prevents a flash. It already exists for the theme.
4. `{@attach}` / `$effect` wrappers around browser APIs that have no declarative form: `IntersectionObserver` (scroll spy), `navigator.clipboard`, `matchMedia('(hover: hover)')`, focus restore.
5. `@utility` definitions in `theme.css` for repeated multi-class patterns (e.g. `eyebrow`). A Svelte component is preferred when markup is involved.
6. Third-party CSS that cannot be avoided (e.g. the YouTube embed).
7. Third-party bootstrap snippets: the Google Analytics `dataLayer` / `gtag` setup (§8).

**Enforcement:**
- ESLint: `svelte/no-inline-styles` (allowing `style:--*` only), `no-restricted-globals` / `no-restricted-syntax` for `document.*` and `window.addEventListener` in `.svelte` files, and `svelte/no-at-html-tags` (allowed only in the one `Prose` component that renders trusted, build-time markdown).
- A small check script fails on `<style>` blocks outside an allow-list and on arbitrary Tailwind values that duplicate a token (e.g. `text-[#1a3009]`).

### 6.6 UI and page-copy translation: Paraglide JS 2 (Q-12)

**Why switch now.** `specs/TRANSLATION.md` chose plain JSON for v1 because it had about 80 strings and Paraglide's router would have competed with ours. Both reasons no longer hold:
- With hub, safeguards and reference-implementation copy in the pages, the string count grows into the hundreds of long strings.
- Today `src/lib/i18n/index.ts` imports **all five locales' JSON into every page's client bundle**. Paraglide compiles each message to a function, so a page ships only the messages it uses, and only in the active locale. Keys are also type-checked.
- Paraglide 2 does not need its own routing. We keep our `[[lang=lang]]` routing and give Paraglide the locale through a custom strategy (`overwriteGetLocale` / `overwriteSetLocale` from `page.data.locale`).

**How:**
- `project.inlang` with `baseLocale: en` and `locales: [en, de, es, fr, pt-br]`; message files stay in `src/lib/i18n/messages/<locale>.json`.
- A codemod migrates the 192 existing keys: dotted keys become valid identifiers (`home.hero.title` → `home_hero_title`) and `m('…')` calls become `m.home_hero_title()`. `{name}` variables already match.
- Page copy is namespaced per page (`safeguards_*`, `refimpl_*`).
- **Inline links in prose** use the same typed references as the YAML (`[[template:purpose-charter]]`, `[[§2.3]]`), rendered by one `RichText` component. That avoids `{@html}` and splitting sentences around links. Longer prose is one message per paragraph.
- `translate.mjs` learns the message files (keyed, with a per-key `sourceHash` sidecar). `check-i18n-keys.mjs` is replaced by Paraglide's compile-time checks plus a missing-key report.
- Server code (`+server.ts`, build scripts) calls messages with an explicit locale, as `t(locale, …)` does today.
- Download-document strings in `scripts/i18n.mjs` move into the same message files, so there is one place for UI strings.

**Spike result (2026-10-02, Paraglide 2.25):** works. A custom strategy is not needed: Paraglide's built-in `url` strategy (optional locale prefix, EN unprefixed) matches our URLs exactly, and `strategy: ['url', 'baseLocale']` never redirects. `paraglideMiddleware` in `hooks.server.ts` gives prerendered pages the right locale (`/de/…` → German, `pt-br` included). In phase 1, `resolveLocale` and `%lang%` in `hooks.server.ts` can switch to Paraglide's `getLocale()`. The cookie and Accept-Language steps never apply to prerendered pages anyway.

### 6.7 Search

## 7. Build pipeline

```
content/**/*.yaml ──► validate (schema + refs + i18n + ownership)
                  ├─► src/lib/server/content/* loaders (typed) ──► prerendered pages + search index
                  ├─► gen: templates md ──► pandoc ──► docx/odt + zips + manifest
                  ├─► gen: core md (+ modules) ──► manifest
                  ├─► PDF: prerendered /standard/core/<v>/print per locale ──► Playwright page.pdf() ──► manifest
                  └─► gen: published standard data (Compass contract + schema.json + manifest)
```

- **One script entry point**: `pnpm content:check` and `pnpm content:build`. The second replaces `build:templates`, `build:core` and the unwired `build-standard-data.mjs`. Generated files stay committed (no pandoc on Vercel). CI fails if the committed outputs are stale, i.e. a rebuild produces a diff.
- **Typed loaders**: the schema is written once (valibot or zod). TS types come from it, and `schema.json` is exported for Compass, which must not import AGPL code, only CC BY data and a schema.
- **Translation**: `translate.mjs` learns YAML. It walks the EN tree, sends only the strings whose `sourceHash` changed, and writes `<file>.<lang>.yaml`. `check-translations` reports per-string drift. The existing `normalize-terms` and `normalize-rfc-keywords` rules become validator checks, so they no longer rewrite files after the fact.
- **PDF of the standard (Q-10)**: printed from the prerendered `/standard/core/<version>/print` page with Playwright (`page.pdf()`), once per locale. That reuses the web typography and the `print:` styles, with no LaTeX/pandoc PDF engine. The PDF gets a cover, a TOC with page numbers (CSS paged media: `@page` margins and running headers), clause anchors as text, and the cite line. It is committed like the other downloads, with a `pnpm content:pdf` step that runs locally or in CI. Modules can get the same treatment later.
- **Tests (new)**: Vitest for the tokenizer, ref resolver, loaders, generators (golden files) and the Compass-contract diff. Playwright smoke tests plus axe for home, one chapter, a template and a stress test.

**Analytics and consent (Q-17)**

Port the setup that ecohubs.community already uses (`src/lib/components/Analytics.svelte` + `CookieConsent.svelte` there). It has proven solutions to the hard parts:
- **Google Consent Mode v2.** Everything defaults to `denied`, and accepting grants `analytics_storage` only; ad signals stay denied permanently. `gtag` must push the raw `arguments` object, which is a known pitfall that is documented there.
- **The banner is server-rendered**, so it does not become the LCP element after hydration. An inline pre-paint check of the stored choice hides it before first paint for returning visitors, so there is no flash.
- The GA script is preconnected and loaded async. The measurement ID comes from `VITE_GA_MEASUREMENT_ID`.

Adapted to this repo's rules:
- The consent state is a small rune-based module (`consent.svelte.ts`) instead of a `window` `CustomEvent`.
- The `dataLayer` / `gtag` bootstrap is listed as **exception 7** in §6.2 (third-party snippet).
- The banner copy goes through Paraglide (5 locales) and uses the AA-contrast tokens.
- The banner links to **`https://ecohubs.community/privacy`** (Q-21). The footer gets a "change cookie settings" link, so the choice can be revoked. That is a GDPR requirement the current ecohubs banner lacks.

**One GA property, one consent choice for both sites (Q-20)**
- rcos.ecohubs.community uses the **same GA4 measurement ID** as ecohubs.community. Reports are split by hostname, and moving between the two sites is one session, not a new referral.
- Consent moves from `localStorage` (per origin) to a **first-party cookie on `.ecohubs.community`**:
  - `ecohubs_consent=accepted|declined`, `Domain=.ecohubs.community`, `Path=/`, `SameSite=Lax`, `Secure`;
  - `Max-Age` of 6 months, after which we ask again (a common supervisory recommendation for consent validity).
  - Both sites read and write it, so a visitor decides once.
  - On localhost the `Domain` attribute is omitted (host-only cookie), because browsers reject it there.
- The pre-paint script reads that cookie (`document.cookie`) to hide the banner before first paint. This is exception 3 in §6.2.
- **Migration:** on each site, if the new cookie is absent but the old `localStorage.cookie_consent` exists, copy the old value into the cookie once. Visitors who already chose are not asked again.

## 11. Review pass: gaps, improvements, simplifications

Second read of this plan, checked against the code. The schema sketches in §4.4 already include the fixes for gaps 1, 2 and 11. Items marked → are actions that belong to the phase they concern.

**Gaps found**
1. **Non-layer chapters have clauses too.** Chapters 9–11 contain numbered items (16, 13 and 10), so the chapter schema must allow clauses everywhere, not only in layers. Chapters 0, 1 and Appendices B and C are mostly prose, so a section needs `blocks` (paragraph, list, table, callout) as well as `clauses`. → Add `blocks` to the section schema alongside `clauses`, in source order.
2. **Tables.** Stress-test maturity ladders and some appendix content are tables. → Add a `table` block type, rendered with a `Table` component. Markdown pipe tables inside prose are not allowed.
3. **Positional translation joins** (`build-standard-data.mjs` joins template sections and glossary terms by position). The migration must **assert** equal counts and matching structure per locale and stop on mismatch, not guess. After migration every string is joined by key, so this class of bug disappears.
4. **`sourceId` / `id` continuity.** Stress-test ids, template ids (`sourceId`) and article ids are referenced by Compass (`sourceId`) and by old `?id=` links. → Keep them as fields, and include `?id=` handling in the redirect map.
5. **Clause renumbering in future versions.** Clause `ref`s can change between versions, and `key` is the stable id. Anchors use `ref` because that is what people cite, and the chapter page also emits `key`-based anchors (`#k-l0.invariants.4`) so that tools can deep-link stably.
6. **Hidden guidance and SEO.** Rendering every guide into the HTML could make chapter pages heavy. Layer 0 is about 25 clauses plus guidance, so this is fine. Budget: chapter HTML under 150 KB gzipped, checked in phase 7.
7. **Print.** A standard gets printed. → Add a `print:` stylesheet via Tailwind `print:` variants: hide the shell and the rails, show guidance only in "with guidance" mode, and print clause anchors as text.
8. **No-JS.** Mega-menu links must exist in the HTML: bits-ui renders the content, and they are also mirrored in the footer. The contents rail and jump-to-clause work without JS (§6.5).
9. **Cite box.** The citation format belongs in `version.yaml` (per version, per locale), not in a component.
10. **The design's homepage clause examples** are UI-message keys today (`home.clause.3_6_2`). → Read them from the standard data by `ref`, so they can never drift from the standard.
11. **Templates are not only prose.** 10 of 22 have fill-in tables, and all share a Ratification Record. → `fill` and `ratification` in the template schema (§4.4).
12. **Fallback when a string is not translated.** Today the fallback is per page, with a banner. With per-string YAML a page can be 95% translated. → Policy: render the EN string, mark it `lang="en"` for screen readers and SEO, and show the page banner if any normative string (clause or section title) falls back. Guidance can fall back silently.
13. **URLs outside this repo.** Old URLs live in Compass `meta.yaml` (`source:`), in already-downloaded docx/odt (absolute links), and in the YouTube and podcast descriptions. → The redirects must be kept permanently, not for a transition period. Update Compass's `source` when re-vendoring.
14. **Process.** Per `AGENTS.md`, every Svelte component goes through the Svelte MCP `svelte-autofixer` before it is committed. That goes into the definition of done for phases 1, 3 and 5.

**Simplifications**
1. **Do not author `normativity`, `layer`, `specSection` or `referencedBy`.** Derive them, as today, so there is one fact in one place.
2. **"Put into practice" needs no data.** It is derived from template `clauses`.
3. **"Tested by" is authored once**, on the stress test, and every chapter derives its list from that.
4. **Drop the separate `(+ .<locale>)` published files** that the generator header promises but never writes. Inline `i18n` in the published data is the contract.
5. **Retire the global graph store.** Each route loads only what it needs.
6. **One `content:build` command** instead of three scripts plus a manual one.

**Risks**
- **Migration fidelity** is the main risk. It is covered by the round-trip proof in phase 2 and by golden-file tests.
- **Compass contract drift.** Covered by a contract diff test, plus `schemaVersion` and `schema.json` in the published data.
- **Translation cost for new guidance.** Layer 0 first. LLM translation through `translate.mjs`, then human review of keywords and aliases.
- **Scope.** This is a rebuild of every page. Phases are ordered so that each one is shippable. If time runs short, phase 4 content for Layers 1–6 and the OG images are the parts to defer.
